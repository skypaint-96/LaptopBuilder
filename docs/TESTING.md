# Testing and validation

The repository separates static validation from destructive integration testing.

## Local static checks

Run from the repository root on a Linux environment with Bash, Python 3, and
PyYAML installed:

```bash
make test
# For a release gate (also used by CI):
make test-strict
```

`make test` is opportunistic: it prints explicit skips when ShellCheck,
`ansible-playbook`, or `pwsh` is missing. A successful exit does **not** mean
those three checks ran. `make test-strict` checks for all three, plus Bash,
Python 3, and PyYAML, **before** running the same suite; missing validators
fail the gate. Install PyYAML with `python3 -m pip install -r
tests/requirements.txt` in an appropriate Python environment. Neither target
builds an ISO, boots a VM, writes a USB, nor validates package availability
against live Arch repositories.

This checks:

- custom USB layout, launcher, configuration setter, and removal of the obsolete mount dependency;
- encrypted secret-bundle creation, checksum validation, decryption, permissions, and insecure-input rejection;
- offline Git bundle creation and cloneability;
- isolated staged-credential and systemd credential wiring;
- Bash syntax and, when installed, ShellCheck findings;
- configuration defaults and invalid dependency combinations;
- official package-list selection, VS Code settings merge, and update/recovery ordering regressions;
- YAML and JSON syntax;
- relative documentation links;
- repository structure and safety assertions;
- TPM token/crypttab completion-state behaviour;
- Ansible playbook syntax when `ansible-playbook` is available;
- PowerShell parser errors when `pwsh` is available.

The checks do not partition a disk, enroll firmware keys, or alter a TPM.

## Continuous integration

The GitHub Actions workflow runs `make test-strict` with ShellCheck, Ansible Core, and PowerShell available; the validator preflight fails instead of silently skipping a missing tool. A separate disposable Arch container resolves every official package name from the current repositories and checks the configured AUR names through the AUR metadata API.

Package resolution proves that names and repository dependencies currently resolve; it does not prove that an AUR PKGBUILD is trustworthy or that an application works on the target hardware.

## Destructive integration test matrix

### Opt-in, file-only QEMU/OVMF ISO smoke test (Linux)

This is an operator-run recipe, **not** a CI job and not a completed test. It
does not set up Hyper-V, attach a host disk, or invoke the USB builder. Run it
only on a Linux machine with `qemu-system-x86_64`, `qemu-img`, and OVMF already
available. Obtain an ISO-only build separately as documented in [USB](USB.md);
verify its SHA-256 against the companion checksum before boot. The recipe uses
an ISO file, a newly created qcow2 file, and a private copy of OVMF variables.
No `/dev/` path or `-usb -device usb-host` belongs in these commands. Check
free disk space and keep the VM directory private. On Arch, `edk2-ovmf`
commonly provides the 4M firmware files below; on other distros locate a
**matching** writable VARS and readonly CODE pair and replace the paths.

```bash
set -euo pipefail
isos=(usb/output/arch-workstation-*.iso)
((${#isos[@]} == 1)) || { echo 'Choose one ISO explicitly instead of a glob' >&2; exit 1; }
iso="$(realpath "${isos[0]}")"
test -f "$iso"
sha256sum -c "${isos[0]}.sha256" # from repository root, as generated by the builder
code=/usr/share/edk2/x64/OVMF_CODE.4m.fd
vars=/usr/share/edk2/x64/OVMF_VARS.4m.fd
test -f "$code" && test -f "$vars"
vm_dir="$(mktemp -d)"
chmod 700 "$vm_dir"
cp -- "$vars" "$vm_dir/OVMF_VARS.fd"
qemu-img create -f qcow2 "$vm_dir/empty.qcow2" 40G
printf 'Disposable VM files: %s\n' "$vm_dir"
qemu-system-x86_64 -machine q35,accel=tcg -m 4096 -smp 2 \
  -drive if=pflash,format=raw,readonly=on,file="$code" \
  -drive if=pflash,format=raw,file="$vm_dir/OVMF_VARS.fd" \
  -drive if=virtio,format=qcow2,file="$vm_dir/empty.qcow2" \
  -drive if=ide,media=cdrom,format=raw,readonly=on,file="$iso" \
  -boot order=d -nic user,model=virtio-net-pci
```

Expect OVMF to boot the ArchISO (Secure Boot disabled), then the tty1
`archws` menu with options 1–9 as listed in [USB](USB.md). Use menu option 7
for diagnostics, 4 to inspect/change configuration, and 8 for a shell; check
`lsblk` identifies only the virtual `/dev/vda` target and the ISO CD-ROM.
This ISO-only image has **no** `ARCHWS_DATA` partition; missing persistent
cache/config is expected, and offline install/refresh/persistence **cannot**
be certified by this smoke test. Do not select install or confirm an erase
just to check the menu. Shut down the guest, then remove only the directory
printed above when no VM is running (`rm -rf -- "$vm_dir"` in that same shell).
The VM commands never open host physical devices, but an install performed
inside the guest would erase the attached **virtual** disk.

### Release integration (separate, opt-in)

Before using an important disk, test a release in a disposable x86-64 UEFI virtual machine with:

1. an empty virtual disk;
2. UEFI variable persistence;
3. Secure Boot Setup Mode and owner-key enrollment;
4. a virtual TPM 2.0;
5. one full install, provision, Secure Boot, TPM enrollment, update, and recovery cycle.

The smoke recipe above covers **only** ISO boot and the menu: it does not
provide a TPM, Setup Mode key enrollment, a writable USB partition, or an
installation. For a full integration run, use a separate disposable VM with
the required virtual TPM/UEFI settings and explicitly set the installer disk
to its virtual disk after checking guest `lsblk`. Never pass through a host
physical disk. Then test on a spare T480 SSD. Confirm Wi-Fi, audio,
suspend/resume, both kernels, Docker, Steam, external displays,
USB-C/Thunderbolt, TPM/PIN unlock, and passphrase fallback. Firmware behaviour
cannot be fully validated by static checks or a virtual machine.

### Hardware support and test matrix

| Target | Supported intent | Minimum release evidence (record firmware, disk, CPU/GPU, result) |
| --- | --- | --- |
| File-only QEMU/OVMF x86-64 | ISO/menu smoke only | ISO checksum, UEFI boot, tty1 menu, diagnostics; no persistence or TPM claims |
| Disposable UEFI VM with vTPM | Generic install path, not physical firmware | Virtual-disk install, both boot entries, update/recovery, Setup Mode/Secure Boot and TPM/PIN/passphrase fallback where configured |
| ThinkPad T480 with spare SSD | T480-specific role | Wi-Fi, graphics/external display, sound, suspend, USB-C/Thunderbolt, both kernels, Secure Boot, TPM/PIN and recovery |
| Non-T480 x86-64 UEFI machine with spare disk | Generic role only; T480-specific role disabled | Record model/firmware, CPU/GPU, Wi-Fi and network, display, suspend, audio, USB boot, both kernels, disk naming, Secure Boot/TPM support and fallback; mark unsupported hardware features N/A rather than pass |

The generic role does not guarantee every non-T480 device, GPU driver,
firmware, or TPM works. Record failed/skipped rows; never infer physical
hardware support from a VM pass.

## Version 0.3 regression coverage

The structural suite asserts ArchISO/profile construction, byte comparison before creating persistent storage, live/cache/embedded fallback, package-source resolution before disk erasure, source-built Paru bootstrap and libalpm repair, single-session sudo/Ansible invocation, automatic target Secure Boot preparation, discovery/signing of every EFI binary, staged credential isolation, resumable first-boot state detection, and signed update repair. A real UEFI integration test is still required to validate firmware key enrolment and TPM behaviour on each hardware model.
